Setup

Assumptions / prerequisites

  • An AWS account and permission to launch a small EC2 (Amazon Linux), plus SSH key ~/Downloads/developer.pem
  • A Tailscale account and Tailnet (admin console)
  • Tailscale client on laptop (and optionally phone) for browse / SSH demos
  • Ability to create an auth key for EC2, and an OAuth client with auth_keys for CI
  • GitHub secrets for Actions: TS_OAUTH_CLIENT_ID, TS_OAUTH_SECRET, EC2_SSH_KEY, EC2_HOST
  • First bootstrap may briefly allow SSH from your public IP until Tailscale is up; day-to-day access uses the Tailnet
  • Dev preview host: development-website.tailc52fb7.ts.net (no public 80/443 required for the demo)

Use case

Private preview of development with no public HTTP

I needed teammates (or myself on another device) to open a dev build of my website without exposing to the public internet. Same pattern as an internal staging site. New features stay on the Tailnet until they're ready for production.

Analogy Like a backstage pass for a show still in rehearsal: cast and crew get in while the public stays out.

The problem

What I didn't want

Open ports

Public 80/443 on EC2 means a crawlable site and a larger attack surface.

Bastion only

Extra jump host to patch which is often a public SSH listener.

Whitelist every teammate

Each time I add someone to a private project, traditionally I would whitelist their IP, then lean on an entire IT team to provision and manage that person's VPN and access. Breaks on travel, home ISP changes, and consumer VPNs that shift egress.

Identity on a Tailnet

Invite the person (or tag the machine). Who they are decides access, not a ticket to update firewall rules. No public port required for the preview.

Access control

Tags = machine identity, not people

tag:dev-server

EC2 portfolio host: a shared server identity, not “my user account.”

tag:ci

Ephemeral GitHub Actions nodes with least privilege for deploy only.

ACL: tag:ci may reach tag:dev-server on port 22 only. Humans use member access for browse/SSH. OAuth is scoped so CI can only create keys for tag:ci.

Analogy Tags are job roles on a badge: "CI runner" may only open the server's SSH closet, not every office on the floor.

Credential choice

Why OAuth in Actions, auth key on EC2

EC2 → auth key

One long-lived server. Bootstrap with tailscale up --auth-key. Stable hostname for MagicDNS.

CI → OAuth client

No reusable join key in GitHub forever. Each run gets a short-lived tagged node; key expiry / blast radius is much better for automation.

Validation

How I proved it works

  • Positive: With Tailscale on → open MagicDNS URL → site loads (dev banner)
  • Negative: Tailscale off → “can't be reached”
  • NordVPN test: Public SSH from a shifted egress IP fails (SG allowlist), so the VM isn't open to the world
  • Tailnet SSH: Same laptop reaches development-website…ts.net over Tailscale without widening 80/443
  • CI: Push to development → Action joins Tailnet → AWS EC2 redeploy succeeds

Comparison

Tailscale vs another VPN service (NordVPN)

Same word “VPN,” different jobs. NordVPN changes your egress. Tailscale builds a private mesh between your machines.

NordVPN · egress tunnel

Traffic leaves through a vendor exit. That new IP does not unlock MagicDNS or your private AWS preview.

Tailscale · mesh Tailnet

Peers talk over WireGuard. Invite a teammate; laptop/phone/EC2/CI share one identity-aware network.

Analogy NordVPN is a disguise on the public street: you look like someone else to the outside world. Tailscale is a membership card for a private club: the bouncer checks who you are, not which street you walked in from. A disguise does not get you past the club door; the card does.

Reflection

What worked well

  • Small scope: one private static site still showed MagicDNS, SSH, tags, and CI
  • Auth key for EC2 + OAuth for Actions matched the docs' intent
  • NordVPN + Tailscale-off negative tests made the story obvious
  • One setup-dev-nginx.sh for humans and CI; SERVER_NAME stays in VM .env
  • Inviting another user to the Tailnet was trivial for “team preview”

Reflection

Difficult or surprising

  • Bootstrap still needs a narrow public SSH (or SSM) before Tailscale is up
  • nginx on Amazon Linux couldn't read ~/app/out until home-dir permissions were fixed
  • First Actions failure was a stale remote branch vs local script fixes: a coordination issue, not Tailscale itself

Technical deep dive

How Tailscale works (WireGuard under the hood)

Tailscale is not “just another VPN app.” The data plane is WireGuard: fast, modern crypto between peers. Tailscale adds the control plane so keys, identity, and ACLs stay manageable.

1 · Keys on each node

Every device generates its own WireGuard keypair. The private key never leaves the device. That is why relays cannot read your traffic.

2 · Coordination server

Nodes register public keys + reachability with the coordination server (control plane). Peers download each other's public keys and allowed IPs for the Tailnet. See How Tailscale works.

3 · Direct WireGuard path

When possible, peers form a direct WireGuard tunnel (NAT traversal via STUN/ICE-style discovery). Encrypted packets go peer-to-peer: laptop ↔ EC2 in this demo.

4 · DERP fallback

If UDP is blocked or NAT is harsh, traffic can relay via DERP. Relays forward already-encrypted WireGuard packets; they do not hold your private keys. Docs: encryption.

Layer What it does in this project
WireGuard (data) Encrypts browse/SSH/CI traffic between laptop, EC2, and the ephemeral Actions node
Coordination + ACLs Who is on the Tailnet; tags like tag:ci → tag:dev-server:22
MagicDNS Names resolve to Tailscale IPs so you never need a public A record for the preview

Check live path type with tailscale status (direct vs relay). That is how I talk about “secure connectivity” without hand-waving.

Analogy WireGuard is the armored truck between two buildings. The coordination server is the dispatcher that shares addresses. DERP is a sealed courier if the direct road is blocked; the courier never has the truck's keys.
